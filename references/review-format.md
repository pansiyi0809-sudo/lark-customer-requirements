# 用户确认预览

先用一句话说明录音归并为几条需求，以及每条包含哪些子功能。候选事项都要在内部草稿中标明去向，但对话里以拟登记记录的字段为主，避免冗长的分析。完整预览直接写在对话中，不以文件链接代替。

草稿 JSON 包含 `source`、`candidates`、`requirements`。每个候选有 `id`、`evidence`、`summary`、`decision`（`register` / `merge` / `exclude` / `unclear`）；前两种需有 `requirement_id`，后两种需有 `reason`。每条需求有 `id`、`fields`、`priority_reason`，可加 `questions`。运行 `python3 scripts/check_draft.py draft.json --schema live-schema.json` 检查每项去向并生成 Markdown；该脚本不连接飞书。

## 对话展示

按实时 schema 顺序列出**所有字段**。有值直接显示，未知或不适用显示“内容为空”，只读公式字段显示“系统自动生成”。下表只是匿名格式示意，不能代替实时字段和选项：

| 字段 | 拟填写内容 |
| --- | --- |
| 子中心 | 已核实的选项 |
| 功能名称 | 项目协作功能 |
| 功能描述 | 允许项目成员共同编辑，并保留变更记录。 |
| 进展 | 已核实的阶段选项 |
| 优先级 | 已确认的等级 |
| 产品负责人 | 已核实的负责人选项 |
| 研发负责人 | 内容为空 |
| 测试负责人 | 内容为空 |
| 需求背景 | 提出人：已确认的姓名 |
| 需求来源 | 已核实的来源选项 |
| 需求ID | 系统自动生成 |

其他字段也必须逐行列出，不要因示例未展示而省略。日期、版本和走查无法确定时直接显示“内容为空”；不为每个空字段写解释。必填项缺少值时在表外集中说明，补齐前不写入。提出人未知时不能写“XXX”。用户修改字段后重新展示完整预览，再等待确认。

## 写入后

简明列出需求名称、系统需求 ID、飞书记录 ID 或链接，以及是否核对成功。提交响应不明时先查重，不盲目重试。
